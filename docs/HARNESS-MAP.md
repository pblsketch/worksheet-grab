## 0. 왜 이 문서가 필요한가

"하네스"는 활동지 프로그램 자체가 아니라, **그 프로그램을 만들고 운영하는 AI에게 주는 매뉴얼·규칙·팀 편성**이다.
현재 하네스는 성격이 전혀 다른 세 가지가 한 폴더(`.claude/`)와 한 파일(`CLAUDE.md`)에 뒤섞여 있다:

- 교사가 활동지를 만들 때 작동해야 할 **제품 로직**과,
- 개발자가 코드를 고칠 때만 필요한 **개발 규칙**이 한 데 엉켜 있어,
- 개발자가 버그를 고칠 때도 제품 파이프라인 전체가 딸려 오고, 제품이 돌 때도 42KB짜리 개발 변경이력이 딸려 온다.

**확정된 결정:** 제품 하네스는 실제로 최종 사용자(교사)에게 **배포된다**. 따라서 경계는 문서 관례가 아니라
**물리 분리 + 배포 매니페스트 + 회귀 테스트**로 강제한다. 개발 개념이 교사에게 한 글자도 새면 안 된다(HARD 경계).

## 1. 3층 모델 (정의)

| 층 | 이름 | 정체 | 대상 독자 | 배포? |
|---|---|---|---|---|
| **1층** | 엔진 | 결정적 Node CLI(조립·검증·렌더). 의존성 0. | (내부) | ✅ 배포됨 |
| **2층** | 제품 하네스 | 교사의 한 문장을 활동지로 바꾸는 AI 팀(에이전트·스킬). 1층 엔진을 구동. | **교사(비개발)** | ✅ 배포돼야 함 |
| **3층** | 개발 하네스 | 코드를 고치는 개발자+AI용 규칙·이력·상태. | 개발자 | ❌ 절대 비배포 |

### 핵심 제약 — 2층은 1층 없이 못 돈다
2층 스킬은 실제로 `node bin/worksheet-grab.js …`(1층 CLI)를 호출한다(README 239줄, 오케스트레이터 스킬).
따라서 **"2층만" 배포는 불가능**하다. 배포 단위는 **{1층 엔진 + 2층 제품 하네스}를 한 벌로 묶은 번들**이며,
여기서 빠지는 것은 오직 **3층**이다.

## 2. HARD 경계 규칙

1. **단방향 누출 0** — 3층(개발) 개념이 2층(제품)으로 흘러선 안 된다. "됐다"는 느낌이 아니라 **개발어휘 grep = 0건**으로 계측한다(§5).
2. **번들 자기완결** — 교사에게 가는 번들은 그 안에서 완결 동작한다(개발 저장소 무의존).
3. **동작 보존(이식성 수정은 예외로 명시)** — 파이프라인·트리거 동작은 그대로. 단 박힌 개발자 PC 절대경로 제거는 "동작 변경"이 맞다(지금은 그 PC에서만 작동) — 배포를 위한 필수 수정으로 정직히 분류한다.
4. **경계는 회귀로 잠근다** — 1회 grep으로 끝내지 않고, 개발어휘가 다시 새면 테스트가 빨간불이 되게 한다(경계 침식 방지).

## 4. 배포 벡터 결정

교사에게 **{엔진 + 제품 하네스}** 를 어떻게 전달하는가.

| 후보 | 평가 | 결정 |
|---|---|---|
| **A1. git clone = 배포** | 루트 `CLAUDE.md`(개발)가 자동 로드돼 개발 컨텍스트 누출 | ❌ HARD 실패, 무효 |
| **A2. Claude Code 플러그인** | 매니페스트가 allowlist라 경계는 단단하나, 엔진(Node CLI)을 플러그인에 담기 어색 | 🔶 후속(엔진 npm 배포 후) |
| **A3. 빌드 스크립트 → 사용자 번들(dist)** | `{엔진+2층+제품CLAUDE+.mcp.json}`만 담고 3층은 뺀 깨끗한 폴더 생성. 엔진이 하네스와 함께 가야 한다는 제약에 최적 | ✅ **채택(1차)** |
| **A4. 저장소 분리** | 완전 격리지만 버전 동기화 부담 | 🔶 후속 |

**결정:** A3(번들 빌드)를 1차 배포 벡터로. A2(플러그인)는 엔진 npm 배포 후 후속.
이 저장소를 여는 **기본 독자 = 개발자**이므로, 루트 `CLAUDE.md`는 개발 전용으로 두고 교사용 진입 지침은 번들 안에 별도 조각으로 넣는다.
