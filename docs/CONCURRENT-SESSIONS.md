## 0. 왜 이 문서가 필요한가 — 2026-07-28 실측

두 세션이 한 작업 트리를 공유했다. 서로의 존재를 몰랐고, 다음이 실제로 일어났다.

| # | 사건 | 근거 |
|---|---|---|
| 1 | **한쪽의 미추적 파일이 다른 쪽 커밋에 쓸려 들어감** | `docs/DECISION-object-resize.md`(A 세션 작성, 259줄)가 B 세션의 `git add -A` 로 커밋 `29f606a` 에 포함됨. A 는 그 사실을 나중에 발견 |
| 2 | **단위 테스트 기준선을 잡을 수 없었음** | A 가 착수 게이트로 `npm run test:unit` 실행 → 실패. 원인은 A 와 무관 — B 가 `showStandards` 기본값을 `false` 로 바꾸는 중이었고 기존 테스트는 아직 옛 기대값이었다. "빨간불이 내 탓인지 남 탓인지" 판별 불가 |
| 3 | **렌더 기준선이 허위 실패로 오염** | `ReferenceError: normalizeObjectives is not defined` (`AssembleWorksheet.js:40`). 그 함수는 같은 파일 223행에 정의돼 있다 — 테스트가 **파일이 쓰이는 도중에** 읽었다. 잠시 뒤 다시 로드하니 정상. 진짜 회귀가 아닌데 회귀로 보였다 |
| 4 | **수정 파일이 3분 만에 3 → 4 → 9 → 14개로 증가** | A 가 작업 계획을 세우는 사이 B 가 계속 저장. A 의 코드 지도(핸드오프 §4)가 지목한 5개 파일이 전부 B 의 편집 대상과 겹쳤다 |

**핵심:** 손실은 아직 없었다(A 의 커밋 `495f3e8` 은 무사하고 B 의 다음 커밋도 A 파일을 건드리지 않았다).
그러나 **측정이 불가능해졌다.** 테스트가 초록인지 빨간지 믿을 수 없으면 R2-1(편집==인쇄) 같은 불변식은
지킬 수단 자체가 사라진다. 이 저장소에서 그건 조용한 인쇄 어긋남으로 나타난다.

## 1. 구조적 해법 — 세션마다 `git worktree`

**권장.** 규율에 기대지 않고 문제를 없앤다.

```bash
# 세션 B 를 위한 별도 작업 폴더(같은 저장소, 다른 디렉터리·다른 HEAD)
git worktree add ../worksheet-grab-sessionB -b feat/세션B-작업명
# 끝나면
git worktree remove ../worksheet-grab-sessionB
```

얻는 것:

- **파일 충돌 0** — 물리적으로 다른 폴더다.
- **HEAD 독립** — 브랜치를 만들어도 남의 커밋을 끌어가지 않는다(§2-2 참조).
- **테스트 기준선이 성립** — 내 폴더는 나만 바꾸므로 빨간불은 100% 내 탓이다.
- 객체 DB 는 공유되므로 디스크 비용이 작고, 병합은 평범한 브랜치 병합이다.

치르는 것: 같은 파일을 둘 다 고쳤으면 병합 충돌이 난다. 다만 그 충돌은 **git 이 보여주는 충돌**이라
조용한 유실보다 압도적으로 낫다.

> 이 저장소에는 선례가 있다 — 순수 리팩터링의 무변경 증명에 기준 커밋을 worktree 로 꺼내 A/B 실행한
> 방식(`docs/HANDOFF-editor-workspace.md`, Phase 5). 같은 도구를 세션 격리에 쓰는 것뿐이다.

## 2. 한 트리를 공유해야만 할 때 — 어기면 남의 작업이 사라지는 규칙

### 2-1. `git add -A` · `git commit -a` 금지 — **경로를 명시해 스테이징한다**

사건 #1 의 직접 원인이다. 남의 미완성 파일이 내 커밋에 들어가면 (a) 내 커밋이 리뷰 불가능해지고
(b) 남은 자기 파일이 이미 커밋된 줄 모른 채 계속 고친다.

```bash
git add src/domain/schema/ObjectCatalog.js test/unit/object-size.test.js   # ✅ 내 것만
git add -A                                                                  # ❌
```

커밋 직전에 **반드시** 확인한다:

```bash
git diff --cached --name-only   # 여기 내 파일만 있어야 한다
```

### 2-2. 브랜치를 만들거나 갈아타지 않는다

**HEAD 는 작업 트리 전체에 하나다.** 공유 트리에서 `git checkout -b` 를 하면 그 순간부터 **다른 세션의
커밋까지 내 브랜치로 들어간다** — 상대는 자기가 main 에 커밋한다고 믿는 채로.

공유 트리에서는 저장소 관례대로 `main` 에 직접 커밋한다. 브랜치가 필요하면 §1 의 worktree 를 쓴다.

### 2-3. 작업 트리를 되돌리는 명령 금지

`git stash` · `git checkout -- <path>` · `git reset --hard` · `git clean` 은 **남의 커밋 안 된 작업을
말없이 지운다.** 특히 `git stash` 는 남의 변경까지 통째로 걷어가므로 공유 트리에서 가장 위험하다.

되돌려야 한다면 내가 만든 파일만, 경로를 명시해서 한다.

### 2-4. 테스트 기준선은 트리가 깨끗할 때만 유효하다

사건 #2·#3 이 여기서 나왔다. 공유 트리에서 남의 파일이 dirty 인 채로 잰 숫자는 **기준선이 아니다.**

- 착수 전 `git status --porcelain` 이 비어 있지 않으면, 그 숫자를 기준선이라 부르지 않는다.
- 굳이 재야 한다면 기준 커밋을 worktree 로 꺼내 거기서 잰다.
- 특히 **렌더 스위트는 실행에 수 분이 걸린다** — 그 사이 남이 저장하면 파일을 반쯤 쓴 상태로 읽는다
  (사건 #3). 오래 걸리는 측정 중에는 소스를 고치지 않는다(내 것이든 남의 것이든).

### 2-5. 시작할 때와 커밋할 때 동시 편집을 확인한다

```bash
git status --porcelain   # 내가 안 건드린 파일이 M 이면 = 누군가 살아 있다
git log --oneline -3     # HEAD 가 내가 아는 것과 다르면 = 그 사이 커밋됐다
```

내가 손댈 파일이 이미 남의 손에 있으면 **거기서 멈추고 사용자에게 알린다.** 나란히 고치지 않는다 —
빨간불의 책임 소재를 잃는 순간 불변식을 지킬 방법이 없어진다.

### 2-6. 작게, 자주 커밋한다

커밋 안 된 표면이 작을수록 사고 반경이 작다. 검증 가능한 세로 조각 하나가 끝나면 바로 커밋한다.
2026-07-28 에 A 세션이 렌더 단계로 넘어가지 않고 스키마 단계만 먼저 커밋한 것(`495f3e8`)이 이 규칙이다 —
덕분에 그 뒤 트리가 계속 흔들려도 잃은 것이 없었다.

## 3. 이 저장소에만 있는 추가 주의

- **렌더 스위트는 직렬 전용** — `npm run test:render` 는 `--test-concurrency=1` 을 이미 포함한다.
  두 세션이 렌더 스위트를 동시에 돌리면 Chrome 인스턴스가 경합해 무작위 실패한다. **렌더를 돌리기 전에
  다른 세션이 돌리고 있지 않은지 확인한다.**
- **`wsg-*` 임시파일** 이 누적되면 디스크가 소진돼 무작위 Chrome 500/타임아웃이 난다. 두 세션이 함께
  돌리면 두 배로 쌓인다 — 실행 전후로 `test/helpers/tmp.js` 의 `sweepStaleWsgTmp()` 를 돌린다.
- **`.claude/` 하위(에이전트·스킬)** 는 여러 세션이 동시에 고치기 쉬운 공용 자산이다. 손대기 전에
  §2-5 확인을 반드시 거친다.

## 4. 요약 — 한 장

| 상황 | 하라 |
|---|---|
| 병행 작업이 예정돼 있다 | `git worktree` 로 세션마다 폴더를 분리한다(§1) |
| 어쩔 수 없이 트리를 공유한다 | 경로 명시 스테이징 · 브랜치 금지 · 되돌리기 금지 · 작게 자주 커밋 |
| 착수하는데 트리가 dirty 하다 | 그 숫자를 기준선이라 부르지 않는다. 내가 고칠 파일이 겹치면 멈추고 알린다 |
| 오래 걸리는 측정 중이다 | 끝날 때까지 소스를 고치지 않는다 |
| 남의 작업을 지우고 싶은 충동 | `stash`/`reset --hard`/`clean` 은 공유 트리에서 금지 |
